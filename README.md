# نظام إدارة المرافق والاستقبال الذكي

نظام إدارة مرافق سكنية/فندقية (شقق وغرف) مدعوم بالذكاء الاصطناعي: نواة حجوزات ومالية وخدمة غرف مبنية على قراءة نظام «زائر»، مع استقبال ذكي للنزلاء ومساعد عمليات للموظفين. عربي RTL، React + TypeScript + Vite + Tailwind وSupabase (PostgreSQL + RLS + Edge Functions).

> `DELIVERY_REPORT.md` يوثق ما نُفذ في هذه النسخة (نواة زائر 0007–0008)، الاختبارات التي نُفذت فعلًا، أثر الترحيل، وما يحتاج قرارًا أو مزودًا. `AUDIT_REPORT.md` يوثق تدقيق النسخة السابقة.

## ما يغطيه النظام

| المجال | الشاشات | الإنفاذ |
|---|---|---|
| إدارة المنشأة | الفروع (ضريبة/منطقة زمنية)، البلوكات والطوابق، أنواع الوحدات، الوحدات، المرافق، أنواع المهام، الخدمات — إضافة/تعديل/أرشفة/حذف آمن | انتماء كل علاقة للفرع، تبعيات قبل الحذف، قفل متفائل، تدقيق قبل/بعد |
| الحجوزات | حجز جديد بعرض سعر خادمي، قائمة بترقيم وتصدير كامل، تفاصيل: تمديد/تقصير، تبديل وحدة، تعديل إجمالي، خدمات، إلغاء، عدم حضور | قيد `EXCLUDE` على التخصيصات الزمنية (لا تداخل حتى تحت التزامن)، كل تغيير بسبب |
| المالية | سندات قبض/تأمين/استرداد/رد تأمين بأربع طرق، الصناديق والحسابات، تسوية الشبكة اليومية، مطابقة المنصات الشهرية، إلغاء سند، فواتير بلقطة ثابتة، دفتر الفرع | دفتر واحد؛ الحالة مشتقة؛ التأمين خارج الإيراد؛ idempotency؛ لا رد زائد؛ كل سند في صندوقه أو حسابه |
| خدمة الغرف | مهام للوحدات والمرافق، إسناد، بدء/إتمام/إلغاء، علامة نظافة، تدوير رموز الصناديق | هدف واحد للمهمة؛ التنظيف لا يحرر وحدة مؤجرة؛ الجاهزية محسوبة |
| الاستقبال الذكي (نزلاء) | محادثة كاملة، خدمات سريعة، توفر وأسعار حية، تحويل لموظف، Kiosk | 4 طبقات حواجز، 13 أداة، مسار حتمي بلا AI |
| مساعد العمليات (موظفون) | زر عائم في كل الشاشات + إحاطة اليوم | يقرأ بصلاحية الموظف فقط، يقترح إجراءات تُنفذ بتأكيد بشري عبر نفس الدوال |

## المبدأ الهندسي

| الطبقة | الدور |
|---|---|
| المتصفح (React) | عرض فقط. لا يحمل أي سر، ولا يقرر أي شيء حساس. |
| PostgreSQL (RLS + دوال `SECURITY DEFINER`) | **مصدر الحقيقة**: بوابة تسليم الرمز، التحقق من ملكية الحجز، تشفير أرقام الوثائق ورموز الصناديق، الكشف التدريجي، التدقيق. |
| Edge Function `ai-reception` | المدخل الوحيد للذكاء الاصطناعي (Gemini). يمر عبر حواجز إدخال/أدوات/إخراج صارمة ويعود تلقائيًا إلى مسار إرشادي ثابت عند أي فشل. |

الذكاء الاصطناعي **لا يرى** رمز أي صندوق ولا أي رقم وثيقة كامل، ولا يستطيع اعتماد هوية أو دفع أو دخول. كل ذلك يبقى بيد المشرف ومحرك القواعد.

## قواعد المال (المرحلة 1، الترحيل 0028)

- **الهللات**: كل مبلغ عدد صحيح موجب من الهللات (حتى 15 رقمًا). الصفر والسالب وكسر الهللة والنص تُرفض في كل سند وفي التسويات (F09).
- **التقريب** (القرار 47): يُقرَّب كل بند على حدة إلى أقرب هللة، والنصف يُجبر بعيدًا عن الصفر (`round` في PostgreSQL و`roundHalfUp` في العرض). الضريبة غير الشاملة = `round(المبلغ × النسبة ÷ 10000)`؛ والشاملة: الصافي = `round(المبلغ × 10000 ÷ (10000 + النسبة))` والضريبة = المبلغ − الصافي. وكل تقسيم لمبلغ على أجزاء (كالسعر الأسبوعي أو الشهري على لياليه في مرحلة تقويم الأسعار) يعطي الباقي للجزء الأخير، فيساوي مجموع الأجزاء الأصل دائمًا.
- **طرق القبض والرد أربع** (القرار 24): نقد، شبكة، تحويل بنكي، آجل عبر المنصة. الطرق السابقة تبقى على سنداتها وتُرفض لكل سند جديد.
- **الصناديق والحسابات** (القرار 25): لكل فرع صناديق نقد وحسابات بنكية، ولكل نوع افتراضي. النقد يُقيَّد في صندوق، والشبكة والتحويل في حساب بنكي مع رقم العملية (3–60 حرفًا، القرار 13)، والآجل عبر المنصة بلا حساب. قيود فقط: لا رصيد تراكمي ولا جرد ولا دفتر أستاذ؛ يكمّلها النظام المحاسبي لاحقًا. المستخدَم يُؤرشف بسبب ولا يُحذف.
- **التأمين** (القراران 33 و69): 50 ريالًا لكل وحدة افتراضيًا (إعداد الفرع)، في دفتر منفصل عن الإيراد، ويُقبض ويُرد في المنشأة نفسها فقط — لا تحصّله المنصة.
- **الضريبة** (القرار 68): إعداد يملكه المالك وحده، وهي صفر الآن. يحفظ كل حجز نسبة فرعه وقت إنشائه، وتُحسب بها كل رسومه اللاحقة؛ تغيير النسبة يسري على الحجوزات الجديدة فقط ويُسجَّل في التدقيق. عند الصفر لا يظهر سطر ضريبة.
- **تسوية الشبكة اليومية** (القرار 13): صافي سندات الشبكة على الحساب نفسه في يوم الفرع (قبض − رد، دون الخصم من التأمين) مقابل إجمالي إيصال الجهاز. الفرق يُحفظ بإشارته مع سببه الإلزامي، والتسوية الواحدة لليوم تُحدَّث بنسختها ولا تتكرر، ولا يُسوّى يوم لم يأتِ.
- **مطابقة المنصات** (القرار 24): كل دفعة «آجل عبر المنصة» تبقى غير مطابقة حتى يُسجَّل إيداع المنصة في الحساب البنكي. المتوقع = القبض − الاسترداد للدفعات المختارة من منصة واحدة؛ الفرق (العمولة عادة) يحتاج سببًا؛ الدفعة تُطابق مرة واحدة، وإلغاء المطابقة للمالك أو المدير ويعيد دفعاتها.

## العرض التجريبي داخل المتصفح (بدون خادم)

```bash
npm run build:demo          # يبني النسخة التجريبية في dist-demo (VITE_DEMO=1)
npx vite preview --outDir dist-demo
```

في وضع العرض يُستبدل Supabase بطبقة بيانات داخل المتصفح (`src/demo/`) تحاكي دوال النظام وقواعده (نطاق الفرع، الأدوار، الدفتر المالي، منع التداخل) على بيانات افتراضية تُحفظ في `localStorage`. حسابات الدخول الجاهزة: `owner@demo.sa`, `manager@demo.sa`, `reception@demo.sa`, `finance@demo.sa`, `housekeeping@demo.sa` (أي كلمة مرور). هذا الوضع للاستعراض فقط ولا يُستخدم في الإنتاج.

## التشغيل محليًا

```bash
npm ci
cp .env.example .env           # ضع VITE_SUPABASE_URL وVITE_SUPABASE_ANON_KEY
npm run dev                    # http://localhost:5173
```

### قاعدة البيانات (Supabase)

1. طبّق الترحيلات بالترتيب من `supabase/migrations/` (`supabase db push` أو عبر SQL Editor).
2. مفاتيح التشفير (رموز الصناديق وأرقام الهويات): على Supabase المستضاف يُنشئها الترحيل 0014 تلقائيًا داخل Supabase Vault وينقل إليها بيانات البذور المشفرة بالمفاتيح التجريبية العامة — لا خطوة يدوية ولا يمر المفتاح بأي ملف. على PostgreSQL محلي/ذاتي الاستضافة بلا Vault اضبطها مرة واحدة:
   ```sql
   alter database postgres set app.keybox_key   = '<32 حرفًا عشوائيًا>';
   alter database postgres set app.identity_key = '<32 حرفًا عشوائيًا آخر>';
   ```
3. أول مستخدم يسجّل من `/staff/login` يصبح **مالكًا** فقط إذا كان `system_settings.demo_mode = true` ولا يوجد موظفون مرتبطون بعد. بعد ذلك تُضاف الحسابات بدعوة من المالك (`/admin/staff`) ويُربط الحساب تلقائيًا عند أول تسجيل دخول بنفس البريد.

### محرك الذكاء الاصطناعي (Gemini)

```bash
supabase functions deploy ai-reception ai-health ai-ops
supabase secrets set GEMINI_API_KEY=AIza... APP_BASE_URL=https://your-domain
```

`ai-ops` (مساعد العمليات) يعمل بتوكن الموظف نفسه؛ بدون مفتاح يعطي إحاطة وإجابات حتمية من بيانات النظام ويبقى قادرًا على اقتراح الإجراءات عبر الواجهة.

ثم من `/admin/ai-settings`: فعّل المحرك، اختر النموذج (`gemini-3.8-flash` افتراضيًا — نماذج Gemini 2.x لم تعد متاحة للمفاتيح الجديدة؛ المحوّل يضبط مستوى التفكير ويعيد «توقيعات التفكير» في خطوات الأدوات كما تشترط نماذج 3.x)، واضغط «اختبار الاتصال». المفتاح لا يُخزَّن في قاعدة البيانات ولا يُعرض في أي واجهة.

**النماذج الاحتياطية** (`ai_settings.fallback_models`، افتراضيًا `gemini-3.6-flash` ثم `gemini-3.5-flash-lite`): Google قد تردّ «503 high demand» على نموذج بعينه لساعات بينما تجيب نماذج أخرى. عند 503/429/404/500/504 يُجرَّب التالي ضمن مهلة الخطوة نفسها، ويُؤجَّل النموذج المتعثر لدقائق، ويُسجَّل `provider_fallback:<النموذج>` في أحداث الحماية؛ أما 400/401/403 فتوقف السلسلة فورًا لأنها لا تتغير بتغيير النموذج. إن انتقلت حلقة أدوات إلى نموذج آخر في منتصفها تُرسل له خطوتها السابقة بالتوقيع البديل الذي توثقه Google بدل توقيع النموذج الأول.

بدون مفتاح، أو عند تجاوز الميزانية اليومية، أو عند انقطاع المزود، يعمل النظام تلقائيًا بالمسار الإرشادي الثابت نفسه (نفس الأزرار والخطوات) دون توقف.

#### طبقات التقنين الصارم

1. **بوابة الإدخال**: كشف حقن التعليمات (عربي/إنجليزي)، رفض المواضيع خارج النطاق (برمجة، سياسة، طب، قانون، مال، فنادق أخرى، أسئلة عن النموذج…)، وحجب أرقام الوثائق والجوالات والبطاقات قبل تخزين الرسالة أو إرسالها للنموذج.
2. **بوابة الأدوات**: 13 أداة فقط مسموح بها، تُنفَّذ على الخادم بنطاق الفرع والجلسة الموثقة؛ أي أداة أخرى تُرفض وتُسجَّل. 6 أدوات لا تعمل إلا بعد التحقق من ملكية الحجز. حد أقصى 3 جولات أدوات لكل رسالة.
3. **بوابة الإخراج**: أي رقم من 4–8 خانات، أو رقم وثيقة، أو جوال كامل، أو رابط غير معتمد، أو صدى لتعليمات النظام، أو ذكر اسم المزود → يُحجب الرد ويُستبدل بالرد الإرشادي، ويُسجَّل الحدث.
4. **الميزانيات**: حد طلبات ورموز يومي، حد رسائل لكل جلسة، مهلة زمنية، وتحويل تلقائي للمشرف بعد 3 محاولات مخالفة.
5. **تعليمات النظام**: 9 قواعد غير قابلة للتجاوز (لا رموز، لا أرقام وثائق، لا اختلاق توفر/أسعار/حجوزات، لا تأكيد دفع/هوية/دخول، لا كشف تعليمات).

## الاختبارات

```bash
npm test                                        # Vitest: 66 اختبارًا (حواجز الاستقبال 54 + مساعد العمليات 12)
PGHOST=... PGUSER=postgres tests/sql/run.sh     # 51 اختبار أمن + 89 اختبار قبول للنواة على PostgreSQL 16
PGHOST=... PGUSER=postgres tests/sql/concurrency.sh   # X01/X02: سباق حجز وسباق استرداد بجلستين حقيقيتين
npm run typecheck && npm run build
```

اختبارات SQL تغطي بنود القسم 24 من المواصفات: عدم كشف البيانات بمعرفة رقم الحجز، عزل الفروع، صلاحيات الأدوار، منع التخصيص المزدوج، الكشف التدريجي، بوابة الرمز بكل شروطها، عدم تكرار الأحداث المالية، تغيير الرمز بعد المغادرة، انتهاء الروابط المؤقتة، والتحقق من بيانات النزلاء.

## حالة التكاملات

| التكامل | الحالة |
|---|---|
| Supabase (DB/Auth/Realtime) | يعمل |
| Gemini (الذكاء الاصطناعي) | يعمل عند ضبط `GEMINI_API_KEY`؛ وإلا مسار إرشادي |
| WhatsApp Business Platform | Awaiting Credentials — الواجهة الخلفية غير مبنية بعد (انظر التقرير) |
| مزود دفع / POS Terminal API | Awaiting Provider — السداد يُعتمد يدويًا بمرجع عملية ومفتاح عدم تكرار |
| التسجيل الحكومي (شموس/الرصد) | غير متكامل؛ خانة تأكيد بمرجع يدوي فقط |
| الفوترة الإلكترونية | غير متكامل |

```
tests/sql/core_tests.sql         اختبارات القبول (A/R/F/H/U/D/X07/AI)

```

## بيئة التطوير الموازية (staging)
